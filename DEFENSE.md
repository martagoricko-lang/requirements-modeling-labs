# DEFENSE — Завдання 1: Домен і модель даних (ER)

## Намір і критерії :
Створити нормалізовану концептуальну ER-модель даних (3NF) для домену електронної комерції з варіативністю товарів. Критерії: уніфікація типів ключів (UUID), відповідність найменувань у spec.md та Mermaid-діаграмі, відсутність фізичних join-таблиць без власних атрибутів.

## Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:
• Розбіжність 1: У початковій графічній діаграмі використовувалися ідентифікатори PascalCase (`CustomerID`, `ProductID`), тоді як у підсумковій концептуальній специфікації та Mermaid ERD застосовано єдиний стандарт `UUID` та `snake_case` (`customer_id`, `product_id`).
  -> Коміт: `docs(spec): create spec.md with entities and Mermaid ERD`

• Розбіжність 2: У початкових вимогах ціна в позиціях замовлення називалася просто `Price`, що створювало плутанину з ціною товару; у spec.md її уточнено як `unit_price` для збереження історичної ціни на момент купівлі.
  -> Коміт: `docs(spec): create spec.md with entities and Mermaid ERD`

• Розбіжність 3: Кардинальність зв'язку `ORDER` ↔ `PAYMENT` вимагала уточнення опціональності: замовлення створюється до оплати, тому зв'язок є опціональним (`1 : 0..1`), а не обов'язковим `1:1`.
  -> Коміт: `docs(spec): create spec.md with entities and Mermaid ERD`

## Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):
Розглядався варіант моделювання зв'язку між `ORDER` та `PRODUCT_ITEM` як чистої M:N зв'язки без додаткової сутності. Обрано створення асоціативної сутності `ORDER_ITEM`, оскільки вона несе власні критичні атрибути бізнес-логіки: `quantity` (кількість) та `unit_price` (фіксовану ціну на момент оформлення замовлення, що забезпечує нормалізацію 3NF при зміні ціни товару в майбутньому).

## Перевірка — узгодженість із попередньою моделлю :
Проведено повну крос-перевірку назв полів і типів даних між текстовим описом сутностей у `spec.md` та декларативним кодом `erDiagram`. Перевірено правильність відображення кардинальностей у згенерованому GitHub рендері Mermaid.
