# Архітектурні рішення (ADR) — Завдання 3

## 1. Вибір механізму резервування складських залишків товару (SKU)

### Контекст і визначення проблеми
Під час оформлення замовлення (`UC-02: Checkout Order`) виникає необхідність обробки складських залишків `stock_quantity` сутності `PRODUCT_ITEM`. Необхідно вирішити, як саме здійснювати резервування залишків при створенні замовлення для запобігання ситуаціям Race Condition (одночасна купівля останньої одиниці товару кількома користувачами).

### Варіанти, які обдумувались
- **Синхронне песимістичне резервування (Pessimistic Locking / Direct DB Reserve):** Перевірка та зменшення залишків у тій самій транзакції бази даних під час виклику `submitOrder`.
- **Асинхронне резервування через чергу повідомлень (Event-Driven / Message Queue):** Створення замовлення без миттєвої перевірки залишків із подальшим надсиланням події в чергу (RabbitMQ/Kafka).

### Рішення
Обрано **Синхронне песимістичне резервування** в межах транзакції створення замовлення `Pending_Payment`.

### Наслідки
- **Добре:** Гарантує строгу узгодженість даних (Strict Consistency), унеможливлює оверселлінг (продаж товару, якого немає на складі), спрощує реалізацію та відладку динаміки системи.
- **Погано:** Збільшує час відгуку (latency) створення замовлення через додаткові блокування таблиці `PRODUCT_ITEM` в БД.

### Наслідки іншого варіанту (Асинхронне резервування)
- **Добре:** Висока швидкість відповіді для користувача та висока здатність обробки пікового навантаження.
- **Погано:** Виникає ризик компенсаційних транзакцій (скасування замовлення вже після підтвердження користувачу, якщо товару насправді не виявилося на складі).
